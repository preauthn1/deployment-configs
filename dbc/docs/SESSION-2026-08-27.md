# 開發紀錄：2026-08-27 ~ 2026-09-02

這段期間的一次連續開發過程摘要，涵蓋 `v0.0.14` ~ `v0.0.29`。照主題整理，不是逐筆 commit 列表；細節請直接看對應 commit。

- 修掉 `install.sh` 兩個實際會踩到的 bug：`trap RETURN/EXIT` 造成的 unbound variable、以及 `curl | bash` 情境下 `main` 永遠不會執行的問題。

## `dbc list` / `dbc start` 顯示

- 兩者都改成照專案分組顯示，欄位順序統一成 `CONN_NAME`、`ROLE`、`PORT`。

## `dbc admin grants`：IAM 群組權限稽核

- 新增指令：稽核 `db-prod-user`（該有 `SELECT`、不該有 `cloudsqlsuperuser`）跟 `db-prod-admin`（該有 `cloudsqlsuperuser`），`--apply` 可自動修正。
- 輸出精簡：預設只印摘要跟異常項目，`--verbose` 才印完整 GRANT 內容；按專案分組顯示。
- **只修正主庫，從庫改成純掃描不動手**——從庫是 `read_only=ON`，直接下 GRANT 會失敗，而且沒必要，GRANT 會透過複寫自動同步。這中間一度改成從庫「完全不檢查」，發現是錯的又改回「真的掃描、只是不執行」。
- 新增**特定實例例外**：`db_prod_user_cloudsqlsuperuser: true`，讓 `db-prod-user` 在某台實例上額外拿到 `cloudsqlsuperuser`（例如開發環境需要讀寫）。主庫跟從庫是各自獨立的設定，必須兩邊都加，否則從庫的正常複寫結果會被誤判成異常，更嚴重的是从庫升級成主庫後 `--apply` 會誤撤銷。目前套用在 `tp-wz3-rd` 全部 5 筆實例（tp-wz3-rd 是開發環境，允許大部份用戶讀跟寫）。

## `dbc admin audit-rules`：Cloud SQL 稽核規則

- 新增指令：檢查/重置每台實例的 Cloud SQL 稽核規則，確保全員的 DML/DDL/DCL 都有稽核。
- baseline 只有兩條規則：全員 DML/DDL/DCL、排除 `mysql.heartbeat` 心跳雜訊（精準指定表，不是整個 `mysql` schema，確保 `mysql.user`/`mysql.db` 仍完整稽核）。
- **不含 DQL**——實測+官方文件確認 Cloud SQL 只稽核主庫、複本完全不會產生稽核紀錄，而日常查詢預設走複本，DQL 規則放在複本上沒有意義。日常查詢的稽核改由 `dbc start` 自己的 proxy 負責（見下一節）。

## 查詢層級稽核（`dbc start` 攔截查詢）

- `dbc start` 攔截通過它的每一條查詢，記錄到 Cloud Logging（`dbc-query-audit`），成功記 `INFO`、失敗記 `WARNING`，內容含呼叫者 IAM 帳號、`connName`、完整查詢文字。這是為了補上 Cloud SQL「複本不稽核」的限制。
- 加一個組好的 `message` 摘要欄位（帳號 @ connName [OK/FAILED] + 查詢片段，截斷前 120 字元），方便在 Cloud Logging 設成摘要欄位看，不用整包 payload 攤開。
- 啟動前會先對每個涉及的 GCP 專案做真實的稽核寫入權限測試（`roles/logging.logWriter`），沒有權限的專案會被拒絕啟動而不是靜默漏記。
- **prepared statement 從「整批拒絕」改成「正常執行並完整稽核」**，細節見下方獨立一節。

## `dbc admin service-accounts`：業務服務帳號管理

- 新增指令：依 `service-accounts.yaml`（gitignored，含明文密碼）建立/同步 BUILT_IN MySQL 服務帳號，統一 `cloudsqlsuperuser` 角色。
- 支援雙密碼輪替（`ALTER USER ... RETAIN CURRENT PASSWORD`）跟 `--discard-old-password` 停用舊密碼；`state: absent` 可刪除帳號（多一層確認）。
- 過程中修掉兩個實際踩到的 `gcloud`/Cloud SQL Admin API 落差：BUILT_IN 帳號一定要明確帶 `--host=%`（不然會建出空 host 的帳號）；`gcloud sql users list` 對 BUILT_IN 帳號會整個省略 `"type"` 欄位（不是給 `"BUILT_IN"` 字串）。
- 新增 `service-accounts.yaml.example` 範本，打包進發版壓縮檔。

## 裸機 MySQL 支援

- `dbc start`/`dbc connect` 現在也能連到不在 GCP 底下的 MySQL（`instances.yaml` 該筆實例加 `host` 欄位即可），純 TCP 轉發、不走 IAM 驗證，`dbc connect` 不會自動帶帳密。
- 查詢稽核邏輯是純協定層的，裸機一樣能用；`dbc admin grants`/`audit-rules`/`service-accounts` 則會自動跳過裸機實例。
- `tp-wz3-rd` 新增一筆裸機實例 `baremetal-vplus33`（`0.0.0.0:3306`）。

## `dbc start` 預設掛載集合的兩種例外

- `no_replica`：主庫沒有從庫可用（chat 系列資料庫），預設模式會一起掛上，不印「請改用從庫」的警告。
- `always_start`（新增）：主庫**有**從庫可用，但仍想讓 `dbc start` 預設一起掛上——跟 `no_replica` 不同，這種情況仍然會印警告，因為從庫是真的存在、日常查詢還是該走從庫。目前套用在 `tp-wz3-rd` 的 `mysql84-new`、`xsgcasino8`。
- 無從庫的提示訊息原本會列出每個實例名稱，因為同名實例會在多個專案重複出現（如 `xsgcasino-online`）造成混淆、且實例一多訊息太長，改成只印筆數，細節請看 `dbc list` 的備註欄。

## `dbc upgrade`

- 新增指令：原地下載並替換目前執行檔（跟 `instances.yaml`），不用重跑 `install.sh`/`install.ps1`。
- `dbc doctor`/`dbc start` 會順便檢查一次有沒有新版本，有的話印提醒。
- **修正 Windows 上會失敗的 bug**：Windows 不允許直接把新檔案 rename 覆蓋掉正在執行中的 exe 本體（`ERROR_ACCESS_DENIED`），只有「改名搬走」本身是允許的。改成兩段式：先把正在跑的執行檔改名搬開成 `.old`，再把新版本搬進原本的檔名；`.old` 因為還鎖著這次刪不掉，留到下次執行 `dbc upgrade` 開頭順手清掉。這是實際 Windows 使用者回報後才發現、修正的。

## prepared statement 從「整批拒絕」改成「正常執行並完整稽核」

- **動機**：工程師在本機用 Laravel 連開發資料庫時卡住——Laravel 的 PDO connector 預設會關掉 emulate prepares（跟一般 PHP PDO 的預設相反），一定會用到 native prepared statement（`COM_STMT_PREPARE`/`COM_STMT_EXECUTE`），撞上原本「整批擋掉」的規則。原本建議改連線設定繞過去（`PDO::ATTR_EMULATE_PREPARES => true`），但工程師希望本機跟正式環境行為一致，不想讓程式碼在兩邊表現不同，所以決定把 dbc 本身補完整。
- **設計**：不是單純解除擋止，而是把實際綁定的參數值解出來、代回 SQL 樣板，記進稽核紀錄——跟一般查詢一樣完整，不留缺口。已支援的參數型別：整數（含 unsigned）、浮點、字串/BLOB、`DECIMAL`、日期時間（含 `TIME` 超過 24 小時/負值的變長二進位格式）。
- **少數情況改成 fail-closed，只擋單次 EXECUTE**（回清楚的 MySQL 錯誤，連線不受影響），不是整個功能關掉：這個連線談成 `CLIENT_QUERY_ATTRIBUTES`（MySQL 8.0.23+ 的協定能力，一般 driver 預設用不到）、綁定了尚未支援解碼的型別（`BIT`/`ENUM`/`SET`/`GEOMETRY` 等）、`?` 佔位符數量跟參數個數對不上。這是刻意的取捨：不知道未支援型別的實際位元組長度，硬解下去會讓後面所有參數全部位移解錯，比完全不解更糟——這也是這個功能唯一敢做的底線，寧可拒絕也不要記一筆看起來合理、實際上是錯的稽核紀錄。
- **`COM_STMT_SEND_LONG_DATA`**（大型 BLOB/TEXT 參數）：內容不記錄（避免撐爆 Cloud Logging 單筆紀錄的大小上限），但會在稽核紀錄裡明確標成「未記錄」，不是靜默略過；同時要正確追蹤哪些參數走這個管道，因為 `EXECUTE` 的數值區塊會跳過它們，沒追蹤到會讓後面的參數全部對不齊。
- **review 流程**：先請 `codex` 做設計審查，抓到原計劃遺漏的幾個地方（`CLIENT_QUERY_ATTRIBUTES` 也會改變 `EXECUTE` 的封包格式、未知型別不能標記後繼續解、long data 需要正確跳過對齊、`COM_RESET_CONNECTION`/`COM_CHANGE_USER` 也要清狀態）；再用 context7 查官方協定文件（含 MySQL server 原始碼裡 `TimeCodec` 的 encode 邏輯）逐項交叉驗證，確認協定理解無誤才動手實作。
- **測試**：純函式（型別解碼、日期時間各種長度變體、`?` 佔位符掃描器要跳過字串常值/反引號識別字/註解裡的 `?`）跟整合後的狀態機（PREPARE→EXECUTE 全流程、各種 fail-closed 情況、`CLOSE`/`RESET`/`RESET_CONNECTION`/`CHANGE_USER` 生命週期、`COM_STMT_FETCH` cursor 分批取結果不會誤觸發稽核）都有單元測試涵蓋 `-race`。另外實際用 Docker 起一個暫時性 MySQL，跑 `go-sql-driver/mysql`（預設走 native prepared statement，跟 Laravel/PDO 是同一種二進位協定）透過 dbc 真正的 proxy 連過去做端到端驗證，測完就把容器清掉了。這個過程中抓到一個測試預期寫錯的地方：原以為 `DECIMAL` 欄位的參數會被送成不加引號的 `NEWDECIMAL` 數字型別，實測發現 driver 是照**綁定的 Go 值型別**（這裡綁的是 Go `string`）決定二進位協定型別，不是照目的欄位的 SQL 型別，所以稽核紀錄裡看到的其實是帶引號的字串——確認是測試預期錯了，不是解碼邏輯的 bug。
- **效能**：量測過解碼一個帶 5 個參數（整數/字串/DECIMAL/DATETIME 混合）的 `EXECUTE`，最壞情況（每次都重新解析型別區塊）約 6 微秒，相對於連到 Cloud SQL 的網路來回（毫秒等級）可忽略不計；稽核紀錄寫入 Cloud Logging 本身是非同步的，不會拖慢查詢。
- README 的「支援 prepared statement」段落跟 GUI 工具連線那段過時的 `useServerPrepStmts` 建議都一併更新。
